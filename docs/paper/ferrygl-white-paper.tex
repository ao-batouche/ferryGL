\begin{abstract}
\noindent
AI agents can now do much of the routine work around software projects, but every run of an
agent costs model tokens, and routine work recurs. This paper argues for \emph{token-free
automation}: deterministic programs that do a routine, rule-based task without a language
model, and that people and agents call instead of doing the task themselves. It presents
\ferry, an open-source tool for one such task. Developers who work in another organization's
repositories, such as a client's, often plan that work in their own team's Linear workspace,
which Linear's GitHub integration cannot reach without the other organization's administrators.
\ferry{} copies the GitHub issues and pull requests a person is part of, one way, into that
workspace, using only the person's own credentials. It keeps no state of its own: the links it
attaches to Linear issues record the GitHub state it last acted on, so a status moves only when
that state changes, and edits made by hand stay. A pure planner separates every read from every
write, so every run can be previewed. In a randomized simulation of \SimScenarios{} histories
(\SimRuns{} runs, with \SimFaultRate{} of writes failing), every safety property held in all
\SimSafetyChecks{} of its checks, and a metamorphic check exposed one order-dependence defect.
Measured workloads, priced at published rates under assumptions that bracket how an agent
behaves, show that an agent doing the job itself would process \TokLeanOpusHundred{} to
\TokPlausibleOpusHundred{} tokens on a run of a 100-item route that finds a few changes, and that
delegating the job to
\ferry{} cuts its cost \CmpSavesMin{} to \CmpSavesMax{} times across \CmpModels{} models from
\CmpProviders{} providers. Under the middle-estimate assumptions, a team of 100 syncing twice a
workday would spend \CmpItselfHundredMin{} to \CmpItselfHundredMax{} a year with agents doing
the job, \CmpDelegatingHundredMin{} to \CmpDelegatingHundredMax{} with agents delegating it, and
nothing on inference with \ferry{} alone.
\par\medskip
\noindent\textbf{Keywords:} token-free automation, AI agents, inference cost, deterministic
automation, one-way synchronization, idempotence, edge-triggered reconciliation, least
privilege, GitHub, Linear
\end{abstract}

\section{Introduction}
\label{sec:introduction}

Many developers do their work in repositories that their own organization does not own. A
consultancy's engineers work in their clients' repositories, a platform team contributes fixes
upstream to the open-source projects it depends on, and partners send pull requests to each
other \cite{gousios2014exploratory, gousios2016work}. Their own team still plans in its own
issue tracker, where it records what needs doing, who is doing it and how far it has come
\cite{bertram2010communication}. The work happens in one organization's repositories and is
planned in another's tracker. This paper is about one instance of that gap: work on GitHub,
tracked in Linear. Linear's GitHub integration links pull requests and issues to Linear issues,
but only for repositories whose GitHub organization has connected it. An organization owner
must make that connection (or, for single repositories, a repository administrator), and
\enquote{it is not possible to connect multiple Linear workspaces to a single GitHub
organization} \cite{linear2026github}. A client's organization is often already connected to
the client's own Linear workspace, if it uses Linear at all (\cref{fig:gap}).

\begin{figure}[t]
  \centering
  \input{figures/gap}
  \caption{The gap \ferry{} fills. Linear's GitHub integration needs the client's
    organization to connect it, and a GitHub organization can be connected to only one Linear
    workspace. \ferry{} instead reads GitHub with the user's own token, read-only, and writes
    to the user's own Linear workspace with their own API key. Repository names and issue
    numbers here and throughout the paper are synthetic.}
  \label{fig:gap}
\end{figure}

People bridge the gap in three ways today. They copy issues and pull requests by hand, and
move each status again whenever something changes on GitHub: toil, in the vocabulary of site
reliability engineering \cite{rau2016eliminating}, which adds to the switching between tools
that fragments developers' days \cite{meyer2017work}. They ask the client to connect its
organization, which is often not theirs to ask. Or they ask a general-purpose AI agent, since agents that reason and call tools can drive both APIs \cite{yao2023react,
yang2024sweagent}. But the work recurs: an agent asked to keep two systems in step pays to read
both again on every run, whether or not anything changed, and its behavior is not guaranteed to
be the same twice \cite{ouyang2025empirical, atil2025nondeterminism}.

This paper argues that such work belongs in \emph{token-free automation}: deterministic
programs that do a routine, rule-based task without running a language model, and that people
and agents call instead of doing the task themselves. The agent keeps the judgment, such as
when to run the task and what to do about an exception, and the program does the repetition,
at the cost of API requests rather than inference. (\enquote{Token-free} refers to model tokens
throughout; such a program still authenticates with access tokens.)

\ferry{} is such a program: a small command-line tool that a person, or their agent, runs by
hand or on a schedule. Using only that person's GitHub token and Linear API key, it gives the
issues and pull requests they are part of Linear issues assigned to them and linked to GitHub,
and keeps their statuses in step. It never writes to GitHub, never touches a teammate's
Linear issue, never deletes anything, and shows every change before making it. Its design rests
on one decision: \emph{the destination is the database}. The link on each Linear issue that
\ferry{} manages records the GitHub state \ferry{} last acted on. Linear can find links by URL,
so \ferry{} needs no state of its own; and because it compares GitHub with the recorded state
rather than with the Linear status, it moves a status only when something happens on GitHub,
and leaves the user's own edits alone in between.

\paragraph{Contributions.} This paper makes four contributions:
\begin{enumerate}[1.]
  \item A design for personal, cross-organization, one-way issue synchronization under least
    privilege. It keeps its state in the destination's link metadata and acts on edges in the
    source's state, which gives idempotent reruns without a database and preserves manual
    edits (\cref{sec:problem,sec:design}).
  \item An implementation whose safety rests on eight explicit invariants, a pure planner,
    and a client interface that cannot express the forbidden writes (\cref{sec:implementation}).
  \item An evaluation of the tool: a randomized, model-based simulation with injected write
    failures, which confirms its safety properties and exposes one defect; a request-cost
    model, validated against a mock of GitHub's API; and a planner benchmark
    (\cref{sec:eval-sim,sec:eval-cost,sec:eval-planner}).
  \item A method to compare an agent that does a routine task itself, an agent that delegates
    it to a token-free tool, and the tool alone: measure the task's reads and writes, then price
    them under assumptions that bracket how an agent behaves. On \ferry's task, across
    \CmpModels{} models from \CmpProviders{} providers, delegating cuts an agent's cost
    \CmpSavesMin{} to \CmpSavesMax{} times on a route of 100 items, and more on larger
    routes (\cref{sec:agents,sec:eval-agent,sec:eval-models}).
\end{enumerate}
The evaluation's scripts and data are released with the paper (\cref{app:reproduce}).

\section{Background and problem statement}
\label{sec:problem}

\subsection{GitHub and Linear}

On GitHub, an \emph{issue} is open or closed; a closed issue has a reason: completed, not
planned or duplicate. A \emph{pull request} is open, closed or merged, and an open pull request
may be a draft. A person can be part of an item as its author, as an assignee, as a reviewer who
has submitted a review, as a requested reviewer, or as the author of one of its commits. A pull
request can declare the issues it closes with keywords such as \enquote{Fixes \#10} in its
description \cite{github2026linking}, and search finds issues and pull requests by author,
assignee, reviewer, requested reviewer and update date \cite{github2026searching}. GitHub's
GraphQL API \cite{graphql2025specification} returns at most 1,000 results per search
\cite{github2026publicschema}, and charges each query rate-limit points: the number of
requests needed to fill every connection the query asks for, divided by 100, against a limit
of 5,000 points an hour for a user \cite{github2026graphqlratelimits}.

In Linear, an issue belongs to a team, has an assignee, and has a status drawn from the team's
workflow; each workflow state has a type, such as \emph{started} or \emph{completed}. An issue
can carry \emph{attachments}, which Linear's interface shows as links, and which this paper
calls links. A link has a URL, a title, a subtitle, and key--value metadata whose
\enquote{values can be any string or number}; attaching the same URL to the same issue again
updates the existing link, and the \code{attachmentsForURL} query returns every link to a URL,
with its issue \cite{linear2026attachments, linear2026schema}. A personal API key acts as its
owner \cite{linear2026gettingstarted}.

\subsection{Problem statement}

A person has a GitHub account~$g$, which can read some repositories owned by others, and a
Linear user~$v$ in their own workspace. They choose \emph{routes}: each route names some
repositories and the Linear team (and, optionally, project) that their work there goes to.
The task is to keep, in each route's team, a Linear issue assigned to~$v$ and linked to each
GitHub item that $g$ is part of in the route's repositories, with a status that follows the
item's state on GitHub. (A pull request that fixes one of those issues may share the issue's
Linear issue, \cref{sec:riders}.) Seven requirements constrain the solution:

\begin{description}[leftmargin=2.2em, style=sameline, font=\normalfont\bfseries]
  \item[R1] \textbf{Least privilege.} Use only the person's own credentials. Read GitHub,
    never write to it, and install nothing in the other organization
    \cite{saltzer1975protection}.
  \item[R2] \textbf{Respect for others' work.} Change only Linear issues assigned to~$v$, and
    never delete anything.
  \item[R3] \textbf{The person's edits win.} A status set by hand in Linear stays until
    something happens on GitHub.
  \item[R4] \textbf{Idempotence without local state.} A rerun never duplicates an issue or a
    link, and the program keeps no server, database or cache.
  \item[R5] \textbf{Data minimization.} Copy as little as possible from repositories that
    belong to someone else \cite{europeanunion2016gdpr}.
  \item[R6] \textbf{No surprise writes.} Show every change before making it, and stop before
    reading GitHub or writing anything when the setup is wrong.
  \item[R7] \textbf{Token-free and deterministic.} Run no language model, so that a run costs
    API requests rather than model tokens, and plan the same changes from the same state of
    GitHub and Linear.
\end{description}

\noindent Syncing in both directions, keeping descriptions or comments in sync, and syncing
every issue of a repository for a whole team, which Linear's own integration does once it is
installed, are not goals. Nor is reacting instantly: webhooks would have to be created in the
other organization's repositories, which needs administrator access there
\cite{github2026webhooks}, so \ferry{} polls.

\section{Design}
\label{sec:design}

\subsection{A run}

A run of \ferry{} has six steps (\cref{fig:run}). It loads and validates the configuration,
then resolves every route's Linear setup: the API key's owner, the team, its workflow states,
and the project and label if configured. A missing team, state, project or label stops the run
before GitHub is read. Then, for each route, it reads GitHub and Linear, plans, prints the plan
and, only when run as \code{ferrygl sync \opt{apply}}, makes the planned changes in Linear.
Without \opt{apply}, a run performs every step except the writes.

\begin{figure}[t]
  \centering
  \input{figures/run}
  \caption{The steps of a run. GitHub is only read. All reads for a route happen before the
    plan, and all writes after it; the planner itself does no I/O. What a run writes to Linear
    is what the next run reads back.}
  \label{fig:run}
\end{figure}

\subsection{What is in scope}
\label{sec:scope}

For each route, \ferry{} runs one GitHub search per enabled \emph{role} (\cref{tab:roles}),
restricted to the route's repositories and, if configured, to items updated since a given date.
It merges the results into one item per URL that keeps every role the person has on it. Each
item has a \emph{kind}, which selects its title template and status rules: \key{issue},
\key{pr} (a pull request the person opened) or \key{involved} (someone else's pull request the
person is part of). Commenting on an item or being mentioned in it does not bring it into
scope, since that would pull in many items touched only in passing.

  \label{tab:roles}

GitHub search has no qualifier for the author of a pull request's commits
\cite{github2026searching}, so the last role is the one expensive part of a run: \ferry{} reads
every pull request in scope that the person did not open, with the authors of its first 100
commits, and keeps those with a commit whose author GitHub links to the person's account.
\Cref{sec:eval-cost} measures what this costs.

\subsection{Homes, and state kept in the destination}
\label{sec:homes}

Each GitHub item has at most one \emph{home}: a Linear issue assigned to~$v$ that has a link to
the item's URL. \ferry{} finds homes by asking Linear for the links to each item's URL
(\code{attachmentsForURL}) and keeping the one on an issue assigned to~$v$. That is the whole of
its lookup. It needs no mapping table of its own, so a rerun after a crash, on another machine,
or months later finds the same homes, and a user may move a Linear issue to another team or
project as long as the new team uses the same status names. Links on issues assigned to anyone
else are ignored, so a teammate's issue that links the same pull request is never touched, and
reassigning an issue hands it off: if the item is still in scope, the next run creates a new
home for the user.

On each home's link, \ferry{} records what it needs to remember as flat metadata keys, which fit
Linear's string-or-number values (\cref{fig:home}): \key{ferrygl\_state}, the GitHub state key
\ferry{} last acted on; \key{ferrygl\_synced\_at}, the start of the run that recorded it;
\key{ferrygl\_kind}; and the format version \key{ferrygl\_v}. When \ferry{} updates a link it
replaces only its own \key{ferrygl\_} keys and keeps any others. These keys, like the state
keys below, live in users' workspaces, so they are a compatibility contract: renaming one would
make every recorded link look changed.

\subsection{From GitHub state to Linear status}
\label{sec:states}

\ferry{} summarizes an item's position on GitHub as a \emph{state key} $\sigma(i)$, one of
sixteen strings such as \key{issue:open:pr\_open} or \key{pr:merged} (\cref{fig:states}). For a
pull request, the key follows from its kind and state and, for someone else's pull request,
from the person's review roles: a pending review request maps to \status{Todo}, even after an
earlier review, because it is the person's turn again. An issue closed as not planned or as a
duplicate has the key \key{issue:closed:not\_planned}. An open issue's key also depends on the
pull requests linked to it (\cref{sec:riders}): it leads to \status{In Review} if one of them is
open and ready for review, and to \status{In Progress} if the open ones are all drafts.

Each key maps to one of five status categories (\status{Todo}, \status{In Progress},
\status{In Review}, \status{Done}, \status{Canceled}), whose names in the team's workflow are
configurable. The mapping has two forms: $\delta_{\text{new}}(\sigma)$ is the status of a newly
created Linear issue, and $\delta_{\text{chg}}(\sigma)$ the status to move to when the state has
changed. They differ only on \key{issue:open:pr\_merged}: the fix has landed but the issue is
still open, so a new Linear issue starts in \status{In Review}, while an existing one keeps its
status, since the work is not done until the issue is closed.

\begin{figure}[t]
  \centering
  \input{figures/states}
  \caption{The sixteen state keys and the Linear status each leads to. For an issue, the first
    matching rule wins: closed, then a linked pull request open for review, then an open draft,
    then a merged one, then none. \key{issue:open:pr\_merged} sets a status only on a new
    Linear issue (dashed): when an existing issue's fix merges while the GitHub issue is still
    open, its status stays as it is.}
  \label{fig:states}
\end{figure}

\subsection{Edge-triggered updates: the person's edits win}
\label{sec:edges}

The central rule compares the current state key $s=\sigma(i)$ not with the Linear status, but
with the state key $\rho$ recorded on the item's home:
\begin{itemize}
  \item If $\rho = s$, nothing happens, whatever the Linear status is.
  \item If $\rho \neq s$ and $\rho$ is recorded, \ferry{} moves the status to
    $\delta_{\text{chg}}(s)$ (an \action{update}) and records~$s$. If the issue already has
    that status, or $\delta_{\text{chg}}(s)$ keeps the status, it only records~$s$ (a
    \action{record}).
  \item If no state is recorded ($\rho=\bot$), this is the link's \emph{first sync}: a link the
    user added by hand, or one \ferry{} just added to an issue the user made. \ferry{} then
    moves the status only to close the issue, to \status{Done} or \status{Canceled}, when
    GitHub says the work is done or canceled and the Linear issue is still open. It never
    reopens an issue, or moves it in any other way, on a first sync.
\end{itemize}
A status therefore moves only on an \emph{edge} in the GitHub state, relative to a memory that
lives in the destination (\cref{fig:timeline}). A level-triggered sync, which computes the
desired status from GitHub on every run, would overwrite the person's edits each time.
Level-triggered reconciliation is the right model when the source of truth should win
continuously, as in the controllers of Borg, Omega and Kubernetes \cite{burns2016borg}. Here
two parties own different things: GitHub owns what happened on GitHub, and the person owns
their own tracker. Recording the last synchronized state and comparing against it is how file
synchronizers tell which replica changed \cite{balasubramaniam1998file, pierce2004unison};
\ferry{} applies the same update detection to the source only, and treats the Linear status as
the person's between edges. \Cref{alg:plan} gives the rule in full, with the cases of
\cref{sec:riders}.

\begin{figure}[t]
  \centering
  \input{figures/timeline}
  \caption{Edge-triggered updates for one pull request and its Linear issue. Run~1 creates
    ENG-12 in \status{In Review} and records \key{pr:open}. The user moves it to
    \status{In Progress}; run~2 sees that the recorded state still matches GitHub and changes
    nothing. Run~3 sees the merge and moves it to \status{Done}. The user then reopens it, and
    run~4 leaves it alone. A level-triggered sync (bottom) would undo both edits.}
  \label{fig:timeline}
\end{figure}

\begin{algorithm}[t]
  \caption{Planning one item $i$, with its linked pull requests $L$ and riders $R$
    (\cref{sec:riders}). $A(u)$ are the links to URL $u$ returned by Linear, $C$ the user's
    issues in the route's team, and $v$ the user.}
  \label{alg:plan}
  \small
  \begin{algorithmic}[1]
    \State $s \gets \sigma(i, L)$
    \State $h \gets$ the first link in $A(\mathit{url}(i))$ on an issue assigned to $v$, if any
      \Comment{the home}
    \If{$h$ exists}
      \State $\rho \gets$ the state recorded on $h$, or $\bot$
      \If{$\rho \neq s$}
        \If{$\rho = \bot$} \Comment{first sync: only close}
          \State $c \gets \delta_{\text{chg}}(s)$ if it is \status{Done} or \status{Canceled}
            and $h$'s issue is open, else none
        \Else
          \State $c \gets \delta_{\text{chg}}(s)$ \Comment{none for \key{issue:open:pr\_merged}}
        \EndIf
        \State emit \action{update}$(h, c)$ if $c$ is a status other than the issue's, else
          \action{record}$(h)$; both record $s$ on $h$
      \EndIf
      \State emit \action{link}$(r)$ for each $r \in R$ not yet linked to $h$'s issue
    \Else
      \State $M \gets \{\, m \in C$ unclaimed, mentioning $i$ or a rider, and linked to no other
        GitHub item $\}$
      \If{$|M| > 1$}
        \State emit \action{skip}$(i, M)$ \Comment{the user decides}
      \ElsIf{$|M| = 1$}
        \State emit \action{adopt}$(i, m)$ under the first-sync rule, and claim $m$
      \Else
        \State emit \action{create}$(i)$ with status $\delta_{\text{new}}(s)$, linking $i$ and $R$
      \EndIf
    \EndIf
  \end{algorithmic}
\end{algorithm}

Two properties follow, and \cref{sec:eval-sim} tests both.

\paragraph{Edits persist.} If a run completes its writes, every home it touched records the
state key it acted on. If, by the next run, the key \ferry{} computes for an item is unchanged,
the first branch applies and the home's status is left alone, whatever the user did to it in
between. (The key of an issue depends on its linked pull requests, so a new review request or a
merge is an edge; \cref{sec:eval-order} shows one case where the key changes although, by the
documented rules, it should not.)

\paragraph{Quiescence.} If neither GitHub nor Linear changes after a run that completed its
writes, the next run plans no writes: every item in scope has a home that records its current
key, and every rider is linked. Reruns are therefore safe to schedule as often as wanted.

\subsection{Pull requests that ride with an issue, and adoption}
\label{sec:riders}

An issue and the pull request that fixes it are one piece of work. When a pull request the
person opened refers to one of their synced issues in the same route, it \emph{rides} with the
issue: instead of a Linear issue of its own, it gets a link on the issue's home, with
\key{ferrygl\_linked\_to} naming the issue (\cref{fig:home}). A pull request refers to an issue
when GitHub lists the issue as one it will close, or when its title or description mentions it
as \code{\#252}, \code{acme/api\#252} or by URL. The issue's state key accounts for its linked
pull requests, so the home follows the issue and its fix together, and the rider's link sets no
status of its own: each Linear issue has one status source. The edge cases follow from that.
A pull request that had a home of its own before it referred to the issue keeps it, and still
counts toward the issue's status; an issue with no home \emph{joins} its pull request's home if
the pull request refers to no other synced issue. A rider's link stays, and keeps counting, when
the reference is later edited out, and a rider never moves its issue's home on its own, even
when the issue leaves the person's scope. Someone else's pull request always gets its own home,
and a pull request that refers to several of the person's issues rides with each of them.

People often create a Linear issue for a GitHub item themselves before they install \ferry.
Before creating a new issue, \ferry{} therefore looks for one of the person's issues in the
route's team that already mentions the item: its URL in the description or in a link, or, for a
route with a single repository, a title ending in \code{\#}\emph{number} with no link to any
other GitHub item. A candidate already linked to a different GitHub item, or already home to
another item, never matches. Exactly one match is \emph{adopted}: \ferry{} adds its link and
applies the first-sync rule, so the adopted issue's status moves only to close it. Several
matches are \emph{skipped}, with their identifiers: the person adds the link to the right one,
and the next run picks it up.

\subsection{Writes, failures and retries}
\label{sec:failures}

Each change is applied in a fixed order: the status first, then \ferry's comment (if comments
are on), then the links. The recorded state therefore changes last: if the status update or the
comment fails, the old state stays recorded, and the next run plans the same change again. Each
change is applied independently, so one failure does not stop the others; the run then exits
with status~1.

Retries follow the idempotency of each request \cite{helland2012idempotence,
fielding2022rfc9110}. A request gets up to three attempts, after waits that honor
\code{Retry-After} up to 60~seconds and are otherwise 2 and then 4~seconds, and one that takes
over 30~seconds counts as a network error. Rate-limited responses (HTTP 429, or GitHub's 403
with \code{Retry-After}) are always retried. Network errors, timeouts and HTTP 502, 503 and 504
are retried only for idempotent requests: every read, a status update, and a link create or
update, which Linear makes idempotent per issue and URL \cite{linear2026attachments}. Creating
an issue or a comment is not idempotent, since Linear may have created it before the connection
failed, so \ferry{} reports the error instead of retrying. If the issue was created, the next
run finds it through the GitHub URL in its description and adopts it, so no duplicate is
created; a comment, however, may be posted twice (\cref{sec:limitations}).

\section{Implementation and safety}
\label{sec:implementation}

\ferry{} \version{} is a Python package of about 1,900 lines in eight modules, with one runtime
dependency, the HTTP client HTTPX \cite{encode2024httpx}. Its structure follows the
\enquote{functional core, imperative shell} pattern \cite{bernhardt2012functional,
moseley2006tar}: \code{plan.py} is a pure function from the GitHub items, the Linear links and
candidates, and the configuration to a list of changes, and everything that talks to the network
lives around it. Its 155 tests run in under a second: each planning test states a scenario in
plain terms, the clients are tested against \code{httpx.MockTransport}, and the commands run end
to end against fakes.

\paragraph{Configuration and commands.} The configuration is a TOML file
\cite{prestonwerner2021toml} in which only the routes are required. Unknown keys are errors, so a
misspelled setting cannot be silently ignored, and a published JSON Schema
\cite{wright2018jsonschema} gives editors completion and inline checks. A complete configuration
can be as short as:
\begin{snippet}
[[route]]
repos = ["acme/api", "acme/web"]
team = "ENG"
\end{snippet}
\code{ferrygl check} confirms that the Linear key works, that the GitHub token can see every
repository, and that each route's team, states, project and label exist; it writes nothing.
\code{ferrygl sync} prints the plan, one line per change, and \code{ferrygl sync \opt{apply}}
prints the same plan and makes it:
\begin{snippet}
acme/api#252  issue     update  ENG-7 Todo -> In Review
acme/api#335  pr        link    -> ENG-7
acme/api#360  issue     create  "Cache the session lookup #360" -> Todo
acme/api#348  involved  adopt   -> ENG-9
4 changes (1 create, 1 adopt, 1 link, 1 update). Run with --apply to make them.
\end{snippet}
The exit status is 0 when everything worked, 1 when a route could not be read or a write failed,
2 for a setup or configuration error (in which case nothing was read from GitHub or written to
Linear), and 130 when interrupted. With comments turned on, every change also posts a Linear
comment that starts with the marker \code{(BY-FGL)}, so people can tell \ferry's changes from
their own.

\paragraph{Invariants.} \ferry{} usually runs in repositories that belong to someone else,
often private ones whose contents are covered by an agreement, so its safety rules matter more
than its features. The repository's contributor guide states them as eight invariants, which
human contributors and coding agents alike must not break without the project owner's decision.
\Cref{tab:invariants} lists each one with the mechanism that enforces it and the evidence from
\cref{sec:evaluation}. Two hold by construction rather than by care. The GitHub client has no
code path that sends a mutation. The Linear client exposes exactly five mutations:
\code{issueCreate}, \code{issueUpdate} with only a state, \code{attachmentCreate},
\code{attachmentUpdate} and \code{commentCreate}. No method can delete an issue, a link or a
comment, or edit a title, a description or a comment, so no bug in the planner can make \ferry{}
do so.

\paragraph{Credentials and data.} \ferry{} sends the GitHub token only to \code{api.github.com}
and the Linear key only to \code{api.linear.app}, and stores neither. A read-only GitHub token is
enough. The Linear key acts as the user, so \ferry's own rules, not the key's scope, keep it to
the user's issues. By default, \ferry{} writes to Linear only the GitHub title and number (the
title template can leave the title out), the repository, the item's URL, its state key, and the
user's role as implied by the kind. It reads descriptions to find the issues a pull request
refers to, but copies one only if the user turns that on, once, when the issue is created. It
never copies GitHub comments, reviews, labels, code, or other people's names or logins. Its own
comments name only GitHub items, states and Linear status names, and it keeps nothing on the
user's machine.

\section{Token-free automation for AI agents}
\label{sec:agents}

An AI agent asked to keep Linear in step with GitHub can do the job in two ways. It can do the job itself: search GitHub for
each role, look up each item in Linear, apply the rules of \cref{sec:design}, and make the
writes, reading every item in scope on every run. Or it can delegate the job to a token-free
tool: run \code{ferrygl sync}, read the plan, run \code{ferrygl sync \opt{apply}}, and report.
Its tokens then go to what \ferry{} prints, a line per change, or \code{No changes.} on a quiet
run, instead of to every item in scope. \Cref{sec:eval-agent,sec:eval-models} measure the
difference.

\paragraph{An interface agents can use.} \ferry{} needs nothing agent-specific: any agent that
can run a command can use it, through the same interface a person uses. Three of its properties
make that safe and cheap. A run previews by default, so an agent can show the plan to its user,
or check it, before it applies it. The output is compact and regular: one line per change, with
the item, its kind, the action and its details, then a one-line summary, and every
\action{skip} line says what decision it needs. And the exit status says what happened.
\ferry's documentation has a page for agents, and its website publishes an \code{llms.txt}
index of the documentation for language models \cite{howard2024llmstxt}. Instructions as short
as these are enough:
\begin{snippet}
To sync my GitHub work into Linear, run `ferrygl sync` and show me the plan.
Run `ferrygl sync --apply` only after I approve it. If a line says skip,
tell me what ferryGL needs. If the exit status is 2, report the error and stop.
Never change GitHub or Linear yourself to do this.
\end{snippet}

\paragraph{Least privilege for agents.} Delegating can also narrow what an agent is able to do.
An agent whose only access to GitHub and Linear is \ferry{} cannot write to GitHub, change a
teammate's Linear issue, or delete anything, whatever it is asked or gets wrong, because the
invariants of \cref{tab:invariants} hold for every caller \cite{saltzer1975protection}. That
guarantee holds only if the agent's shell is limited to the \code{ferrygl} commands and the
credentials are kept out of its reach: an agent with an unrestricted shell and the keys in its
environment could call either API directly.

\paragraph{A general pattern.} The same split applies wherever an agent is asked to do routine,
rule-based work again and again: keeping trackers in step, triage by fixed rules, recurring
reports. Once a task's rules are known, writing them into a program moves the task's marginal
cost from inference to API requests, and makes its behavior repeatable. The program is written
once, tested and shared; the agent decides when to call it and reads what it reports
(\cref{sec:related} places this among other ways to make agents cheaper).

\section{Evaluation}
\label{sec:evaluation}

The evaluation asks four questions. Do the safety invariants hold over long, random histories in
which GitHub changes, the user edits Linear, teammates link the same items, and writes fail
(\cref{sec:eval-sim})? What does a run cost in GitHub requests and rate-limit points, and in
planning time (\cref{sec:eval-cost,sec:eval-planner})? What would an AI agent spend to do the
same job itself, or by delegating it to \ferry{} (\cref{sec:eval-agent})? And how does that vary
across models and providers (\cref{sec:eval-models})? All of the data is synthetic.

\subsection{Randomized, model-based simulation}
\label{sec:eval-sim}

\paragraph{Method.} The simulation runs \ferry's own reading, planning and writing code,
unchanged, against two in-memory stand-ins with the same methods as its GitHub and Linear
clients. The GitHub stand-in answers each role's search from a model of issues and pull
requests, in the shape of GitHub's GraphQL nodes, so \ferry's result parsing and reference
detection run too. The Linear stand-in keeps issues, links and comments, and follows Linear's
documented behavior: links are returned by URL across the workspace, up to 20 per URL, and
attaching a URL an issue already has updates that link. As in property-based testing
\cite{claessen2000quickcheck}, each scenario is generated at random from a seed: one or two
repositories, a random configuration (each role on with probability at least 0.85, comments on
or off), and a few initial items. Then, for \SimSteps{} steps, random events happen and \ferry{}
runs. GitHub events open and close issues, open, ready, draft, merge, close and reopen pull
requests, request, give and withdraw reviews, assign and unassign the user, add and remove
references, and push commits. Linear events have the user move statuses, hand issues to a
teammate, link items by hand and write issues that mention items, and have a teammate link the
same items and the user add their own metadata to \ferry's links. Three in ten steps change only
Linear. Each step runs \ferry{} up to four times: a preview; an apply in which \SimFaultRate{} of
writes fail, half of them \emph{lost} (they reach Linear but lose their response) and half
\emph{rejected}; a clean recovery run if any write failed; and a final clean rerun.

After every run, the simulation checks the properties of \cref{tab:sim} against the stand-ins'
state and the writes \ferry{} sent. GitHub descriptions in the model carry a secret marker and
mention other users, so \emph{minimal data} can check that no write carries either, and that no
comment carries a GitHub title; description copying, which is off by default, stays off, so this
checks the default configuration. \emph{Order independent} is a metamorphic relation
\cite{chen1998metamorphic, chen2018metamorphic}: planning the same inputs with every list of
Linear lookup results reversed must give the same changes, since Linear promises no particular
order. Reversal is a single permutation, so the check can expose order dependence, but cannot
show its absence.

\paragraph{Results.} \SimScenarios{} scenarios produced \SimEvents{} events, \SimRuns{} runs and
\SimWrites{} writes, of which \SimFaultsInjected{} failed. The plans included
\SimActionCreate{} creates, \SimActionUpdate{} updates, \SimActionLink{} links,
\SimActionRecord{} records, \SimActionAdopt{} adoptions and \SimActionSkip{} skips, so every
action was exercised. The whole simulation takes about ten seconds. Every safety property held
in every one of its \SimSafetyChecks{} checks (\cref{tab:sim}). Write failures left
\SimOrphans{} Linear issues created without their links; the next clean run adopted all
\SimOrphansAdopted{} of them through the URL in their description, and every recovery converged
in one run.

\paragraph{A finding: order dependence.}
\label{sec:eval-order}
The metamorphic check failed in \SimViolationsOrderIndependent{} of \SimChecksOrderIndependent{}
non-trivial checks, all with the same cause. A pull request that refers to two of the user's
issues rides with both, so its URL is linked from both of their Linear issues. If one reference
is later edited out, the planner looks up the pull request's links and takes the first one on
one of the user's issues as the pull request's own. When that first link is on the issue it still refers
to, the pull request rides with that issue only and stops counting toward the other issue's
status: that issue's state key changes, say from \key{issue:open:pr\_open} to \key{issue:open},
and its Linear issue moves back to \status{Todo}. When the first link is on the other issue, the
rule of \cref{sec:riders} applies as documented (the link stays and keeps counting), and nothing
moves. Linear promises no order for these results, so the outcome is not determined. The
planner itself is still pure; what fails is its invariance to the order of an input that is
semantically a set, and with it requirement R7 and the documented rule for riders. The case is
narrow (a pull request that refers to several of the user's issues and then drops one
reference) and moves only the status of the user's own issue. A fix is to choose among a pull
request's links deterministically, preferring a link on the home of an issue it still refers
to, and to keep counting the pull request toward the status of every issue whose home has its
link.

\subsection{Request cost}
\label{sec:eval-cost}

\paragraph{Method.} The cost experiment runs \ferry's real GitHub client against a mock of
GitHub's GraphQL endpoint, built on \code{httpx.MockTransport}, that pages results as GitHub
does and stops at 1,000 results per search. The repository holds a fixed set of the user's own
items (12 issues, 8 pull requests) and a growing number of other people's pull requests; one in
ten requests the user's review, one in ten was reviewed by them, one in twenty is assigned to
them, and one in twenty has one of their commits. Per route, \ferry{} sends one query for the
token's login and, for each enabled role with $n$ results, $\max(1, \lceil n/50 \rceil)$
search pages, or $\max(1, \lceil \min(N, 1000)/25 \rceil)$ pages for the commit scan over $N$
pull requests the user did not open. GitHub's cost formula \cite{github2026graphqlratelimits}
charges by the sizes a query asks for, not the results it returns. A search page asks for 50
items with up to 20 closing references each, which needs 51 requests to fill and costs 1 point.
A commit-scan page asks for 25 pull requests, each with 20 closing references and 100 commits of
up to 5 authors, which needs $1 + 25 + 25 + 25 \times 100 = 2{,}551$ requests and costs 26
points.

\paragraph{Results.} At every size, the requests \ferry{} sent matched this model, and none was
a mutation. \Cref{fig:cost} shows the result. Without the commit scan, a route with 1,000 other
pull requests in scope costs 9 requests and 9 points. With it, the same route costs 49 requests
and 1,049 points, about a fifth of a user's hourly 5,000; the scan accounts for 40 of the
requests and 1,040 of the points. Beyond 1,000 pull requests, GitHub's limit on search results
truncates the scan: the cost stops growing, but pull requests past the 1,000th are no longer
checked, so some of the user's commits go unseen. This is why \ferry's documentation recommends
setting \code{since}, which bounds every search by update date, and turning
\code{prs\_with\_commits} off when the role is not needed.

\subsection{Planner time}
\label{sec:eval-planner}

A benchmark times the planner alone, on synthetic routes of 10 to 10,000 items, four in ten of
them issues, three in ten the user's pull requests (most referring to an issue) and three in
ten other people's, as the median of seven runs on an AMD Ryzen~9 9950X3D with CPython 3.12.
When every item has a home, one in ten with an out-of-date recorded state, planning time grows
linearly: 0.38~ms for 100 items and 46~ms for 10,000. When a fifth of the items are new, the
planner also matches each new item against each of the user's issues for adoption, so its time
grows faster than linearly, to 288~ms for 10,000 items, far more items than one person is
usually part of. Either way, a run's time is dominated by its network requests.

\subsection{What an AI agent would spend, and what delegating to \ferry{} saves}
\label{sec:eval-agent}

\paragraph{Method.} No agent was run for this paper. Instead, the experiment measures the work
each strategy of \cref{sec:agents} implies, and prices it. It runs \ferry{} through stand-ins
that record every call, over \AgentRuns{} runs of random histories generated as in
\cref{sec:eval-sim}, without injected failures, and over single routes of 10 to 800 items, with
the commit scan off, in which a twentieth of the items change on GitHub between runs. For an agent
doing the job itself, the stand-ins record the size of each result it would have to read and of
the arguments of each call it would have to send, if its tools returned exactly what \ferry's
queries return. For a delegating agent, they record what \ferry{} prints, which is all it reads.
A cost model then prices each agent loop:
\begin{itemize}
  \item An agent doing the job itself starts each run with \ferry's rules as instructions (its
    sync rules and link-metadata convention, about 9,700 characters), nine tool definitions
    shaped after \ferry's reads and writes (about 2,600 characters), the 286-token tool-use
    system prompt \cite{anthropic2026pricing}, and a short request to sync: about
    \AgentFixedLean{} tokens. A run has three dependent steps (read GitHub and the Linear setup;
    look up the links to each item; write) and a closing turn, and a step takes one turn per
    batch of parallel tool calls. Letting all of a step's writes share a turn favors the agent,
    since a link can only be added once its issue exists.
  \item A delegating agent starts with a five-sentence instruction, which, unlike the one in
    \cref{sec:agents}, lets it apply the plan without asking, and the bash tool, whose
    definition adds 325 tokens to the tool-use system prompt \cite{anthropic2026pricing}: about
    \AgentFixedLeanDelegating{} tokens. It runs \code{ferrygl sync}, reads the plan, runs
    \code{ferrygl sync \opt{apply}}, reads the result, and reports, in three turns.
  \item Prompt caching is on: each turn reads the previous prompt from the cache and writes only
    what is new. Scheduled runs are hours apart, so each run starts with a cold cache.
  \item Prices are Anthropic's published rates for Claude Opus~5.5, Sonnet~5.5 and Haiku~5.5,
    including Haiku~5.5's fivefold rates for prompts over 100,000 tokens
    \cite{anthropic2026pricing}.
\end{itemize}
\emph{Tokens per run} counts every token the model processes: the input of every turn,
including the cached prefix each time it is read, plus the output. A cached token costs a
tenth or less of a fresh one, so dollars, not tokens, measure the saving. Two sets of
assumptions bracket how an agent behaves (\cref{tab:assumptions}), and both strategies are
priced under both. The \emph{lean} assumptions give the
agent every advantage, so they approach the least an agent could spend. The \emph{plausible}
ones are a middle estimate, not a worst case: general-purpose GitHub and Linear tools return
fuller records than \ferry{} reads, so an agent using them would read more.

\begin{itemize}
  \item \textbf{Delegating cuts the cost many times over, more the larger the route.} A

    \DelegationSavesEightHundredHigh{} times less at 800. After the first run, its cost grows
    only slowly with the route, because \ferry{} prints a line per change, not per item:
    \TokLeanDelegatingOpusHundred{} to \TokPlausibleDelegatingOpusHundred{} tokens at 100 items,
    and \TokLeanDelegatingOpusEightHundred{} to \TokPlausibleDelegatingOpusEightHundred{} at
    800. What remains is mostly its own instructions and reasoning.
  \item \textbf{A run that finds nothing new costs almost as much.} An agent that reads the
    whole scope learns that nothing changed only after reading it. On the same route, a run that
    finds nothing new reads fewer tokens (\QuietTokLeanOpusHundred{} to
    \QuietTokPlausibleOpusHundred{}) but still costs \QuietRunLeanOpusHundred{} to
    \QuietRunPlausibleOpusHundred{} on Opus~5.5, against \RunLeanOpusHundred{} to
    \RunPlausibleOpusHundred{} for a run that finds \CmpChanges{} changes. In the random
    histories, each applying run is followed by a rerun that finds nothing new, and those reruns
    account for \HistPlausibleOpusQuiet{} of the agent's spend.
  \item \textbf{An agent's own cost grows faster than its scope.} Its context grows with every
    item read, and is read again on every turn. At 400 items, the plausible agent processes
    \TokPlausibleOpusFourHundred{} tokens per run, \MonthPlausibleOpusFourHundred{}
    a month on Opus~5.5 at two runs a workday. Haiku~5.5's long-prompt rates show as a jump once
    prompts pass 100,000 tokens, past 100 items under the plausible assumptions and past 200 under
    the lean ones. The longest prompt, \PeakLeanHundred{} to \PeakPlausibleHundred{} tokens at 100
    items, reaches \PeakLeanEightHundred{} to \PeakPlausibleEightHundred{} at 800, which only
    models with long context windows can hold. The first
    run, which creates every Linear issue, costs \FirstRunLeanOpusHundred{} to
    \FirstRunPlausibleOpusHundred{} on Opus~5.5 for 100 items.
  \item \textbf{A smaller model costs less, at a risk not measured here.} Sonnet~5.5 halves the
    cost of Opus~5.5, and Haiku~5.5 cuts it by more than an order of magnitude at modest scope.
    Whether a smaller model applies \ferry's rules reliably is exactly what this estimate cannot
    say; a delegating agent needs only to run two commands and read their output.
\end{itemize}

\paragraph{Interpretation.} For one person with a modest route, an agent's bill is small in
absolute terms: \MonthLeanSonnetHundred{} to \MonthPlausibleOpusHundred{} a month on Sonnet or
Opus at two runs a workday, and under a dollar on Haiku. The case for token-free automation
rests less on the size of the bill than on its shape. An agent's own cost recurs on every run,
including the runs that find nothing to do; it grows with the route and the schedule; and it
multiplies with every person who runs it. It also buys no guarantees: the estimate assumes the
agent applies the rules correctly every time, which language models do not promise
\cite{ouyang2025empirical, atil2025nondeterminism}, and a run that gets one wrong (a status
moved over the user's edit, a duplicate issue, a teammate's issue changed) costs more than its
tokens. Delegating shows that the two are not alternatives: an agent that runs \ferry{} keeps its
judgment for the decisions that need it, such as when to run and what to do about a skipped
item, spends a few thousand tokens per run on them, and inherits \ferry's guarantees.

\paragraph{Limits of the estimate.} This is a model of agents, not a measurement of them.
Reasoning tokens per turn, calls per turn and turns per run are assumptions, chosen in the lean
case to favor the agent. Every provider is given Anthropic's tool-use overhead (286 tokens, and
325 more for the bash tool), since not all publish theirs, and Claude's tokenizer is not public,
so measured ratios stand in for it. Both strategies read the whole scope on every run, because
\ferry{} does: an agent that kept a watermark and searched only for items updated since its
last run would read far less on quiet runs, at the price of keeping state of its own, and
\ferry{} could do the same. The model does not represent context windows: past a few hundred
items, an agent on a model with a shorter window would have to split a run or compact its
context. Finally, the agents'
correctness, determinism and latency are not measured. Running real agents with these tools
over the same histories would replace the assumptions with measurements, and would also count
how often an agent doing the job itself breaks the invariants of \cref{tab:invariants}.

\subsection{Across \CmpModels{} models from \CmpProviders{} providers}
\label{sec:eval-models}

\paragraph{Method.} This experiment repeats the estimate on \CmpModels{} current models from
\CmpProviders{} providers: for each provider, its flagship and at least one cheaper model, among
them the leading open-weight models as served by their makers (\cref{tab:models}). Everything
but the model is held fixed: the measured workload (one user's route of 100 items, on a run that
finds \CmpChanges{} changes to make, with \CmpRequests{} requests to GitHub and Linear), the
three strategies, and the lean and plausible assumptions. Three inputs vary by model, each from
a published source read on 19 October 2026.
\begin{itemize}
  \item \textbf{Prices.} Each provider's standard API prices for input, cache writes, cache hits
    and output, under its own caching rules: whether a cache write costs more than input, the
    shortest prompt it caches, and any higher price for long prompts \cite{anthropic2026pricing,
    anthropic2026caching, openai2026pricing, google2026pricing, xai2026pricing,
    deepseek2026pricing, moonshot2026pricing, alibaba2026pricing, zai2026pricing,
    minimax2026pricing, mistral2026pricing}. Where a price is set to rise on an announced date,
    the later price is used, since the comparison looks a year ahead; where some hours cost
    less, the full price is used.
  \item \textbf{Tokenization.} The open-weight models' own tokenizers, run on the text of the
    workload (\cref{tab:tokenizers}). JSON tool results, most of what an agent reads, come to
    only 2.4 to 2.9 characters per token, well below the four characters per token often assumed
    for prose. Claude, GPT-6, Gemini, Grok, Mistral Large~4 and MiniMax-M3.1-Flash have no public
    tokenizer, and take the measured median (plausible) or maximum (lean), per kind of text; the
    measured set includes OpenAI's published \code{o200k\_base} as one proprietary tokenizer.
  \item \textbf{Speed.} Each model's output speed and time to first answer token on its maker's
    API, as measured by Artificial Analysis with a 10,000-token prompt, in the fastest
    configuration it measured \cite{artificialanalysis2026}. A turn takes that time, which
    includes the model's reasoning, plus its visible output at that speed, plus its requests,
    which run in parallel within a turn. \ferry's requests run one after another, at an assumed
    0.5 seconds each. No speed was measured for \CmpUntimed{} models, whose times are left out.
\end{itemize}
The schedule and team size are the same for every model: two runs a workday (44 a month) or
hourly over an eight-hour workday (176 a month), for one user and for teams of 10, 50 and 100,
each user with a route of their own. \ferry{} on its own spends no tokens. On a user's machine it
costs nothing; in GitHub Actions, each run is a job billed as one minute, at \$0.006 a minute
for a private repository \cite{github2026actionspricing}, and a user's
\CmpActionsMinutesMonth{} runs a month fall well within the \CmpActionsFreeMinutes{} minutes
GitHub Free includes \cite{github2026actionsbilling}. The comparison counts every minute as paid,
as an upper bound.

\paragraph{Results.} \Cref{fig:models} shows the results, and \cref{tab:models} gives them per
model; the data have every combination of model, strategy, assumptions, schedule and team size.
\begin{itemize}
  \item \textbf{At team scale, an agent doing the job itself costs from hundreds to tens of
    thousands of dollars a year.} For a team of 100 at two runs a workday, it costs
    \CmpItselfHundredMin{} to \CmpItselfHundredMax{} a year, depending on the model, under the
    plausible assumptions, and \CmpItselfLeanHundredMin{} to \CmpItselfLeanHundredMax{} under
    the lean ones, processing \CmpTokensYearMin{} to \CmpTokensYearMax{} billion tokens a year
    (plausible). Hourly runs cost four times as much.
  \item \textbf{The choice of model spans two orders of magnitude.} The dearest flagship costs
    \CmpSpread{} times as much as the cheapest small model, and within one provider the flagship
    costs \CmpWithinMin{} to \CmpWithinMax{} times as much as the cheapest model.
  \item \textbf{Delegating to \ferry{} cuts every model's bill} \CmpSavesPlausibleMin{} to
    \CmpSavesPlausibleMax{} times under the plausible assumptions (\CmpSavesMin{} to
    \CmpSavesMax{} times across both sets), to \CmpDelegatingHundredMin{} to
    \CmpDelegatingHundredMax{} a year for a team of 100, because the agent reads \ferry's plan
    instead of every item.
  \item \textbf{\ferry{} alone spends nothing on inference}: \$0 on users' own machines or within
    GitHub Actions' free minutes, and at most \CmpActionsHundredYear{} a year for a team of 100 on
    paid minutes. That is less than an agent doing the job itself costs on any model, even under
    the lean assumptions. A delegating agent costs less than that on the \CmpBelowActions{}
    cheapest models, but it still needs \ferry{} to run somewhere, so its cost comes on top.
  \item \textbf{\ferry{} alone is also the fastest}, by this estimate. A run takes about
    \CmpFerryglSeconds{} seconds, nearly all of it its \CmpRequests{} requests at the assumed
    half second each. An agent doing the job itself takes \CmpItselfSecondsMin{} to
    \CmpItselfSecondsMax{} seconds, although its requests run in parallel, and a delegating
    agent, which runs \ferry{} twice, \CmpDelegatingSecondsMin{} to \CmpDelegatingSecondsMax{}
    seconds. Models measured only with long reasoning take minutes.
\end{itemize}

\paragraph{Caveats.} Prices change often, and several here are introductory, set by the time of
day, or for a preview (notes a to c of \cref{tab:models}); the script reruns the comparison from
a table of prices. Speeds were measured by a third party, on prompts that ask for longer answers
than an agent's tool calls. A model measured only with reasoning on is likely slower here than
it would be on short tool calls; a model measured without reasoning is timed in a faster
configuration than the one whose reasoning tokens are priced, which favors it. Open-weight
models are counted with their published tokenizer, which the hosted model may not match
exactly. Flat-fee subscription plans, and batch discounts, which do not suit an interactive
loop, are not modeled.

\subsection{Threats to validity}

The simulation's conclusions are only as good as its stand-ins. They follow Linear's and
GitHub's documented behavior, but real services differ in details the stand-ins leave out, such
as the order of results (which the metamorphic check varies), eventual consistency between a
write and the next read, and rate limiting. Reads and writes against a real Linear workspace had
not yet been exercised at the time of writing; GitHub reads have been exercised against a real
repository. The random histories follow hand-chosen event weights, so they cover the rules'
cases broadly but do not represent any real person's work. The cost model relies on GitHub's
published formula, which GitHub may change, and the benchmark ran on one machine. The agent
comparison is a cost model built on measured workloads, not a run of an agent;
\cref{sec:eval-agent} lists its limits.

\section{Related work}
\label{sec:related}

\paragraph{Synchronization and replication.} File synchronizers detect updates by comparing each
replica with an archive of the last synchronized state \cite{balasubramaniam1998file,
pierce2004unison}; optimistic replication generalizes this, with conflict detection and
resolution when both sides change \cite{saito2005optimistic, terry1995managing}, and
conflict-free replicated data types avoid conflicts by construction \cite{shapiro2011conflict}.
\ferry{} has no conflicts to resolve, because it splits ownership: the GitHub state is
authoritative for edges, and the user for everything in between. It also keeps the archive in
the destination, in link metadata, rather than on the synchronizing machine. Bidirectional
transformations, or lenses, propagate edits of a view back to its source
\cite{foster2007combinators}; \ferry's Linear issues are a lossy, one-way view whose edits never
flow back.

\paragraph{Integration and reconciliation.} In the vocabulary of enterprise integration patterns
\cite{hohpe2003enterprise}, \ferry{} is a polling consumer and message translator whose receiver
is made idempotent by looking up earlier results by key, here the GitHub URL, the kind of
repeated work that distributed systems must make harmless \cite{helland2012idempotence}. A
proposed \code{Idempotency-Key} header would let HTTP clients retry creates safely
\cite{jena2025idempotency}; Linear's API offers a similar means, an identifier the client
chooses for each issue or comment it creates \cite{linear2026schema}. Kubernetes-style
controllers reconcile continuously toward a desired state \cite{burns2016borg}; \ferry{} illustrates
why that level-triggered model is ill-suited when the destination has an owner of its own, and how
recording the last acted-on state turns polling into edge-triggered updates.

\paragraph{AI agents, tools and their cost.} Language-model agents that interleave reasoning with
tool calls \cite{yao2023react} can work in repositories and resolve real GitHub issues
\cite{yang2024sweagent, jimenez2024swebench}, so such an agent could do \ferry's job. But these
models are not deterministic in practice, even with settings meant to make them so
\cite{ouyang2025empirical, atil2025nondeterminism}, and they cost tokens on every run. Models can
learn to call tools \cite{schick2023toolformer}, act through executable code
\cite{wang2024codeact}, and write tools for later use \cite{cai2024tool}, and protocols such as
the Model Context Protocol connect agents to them \cite{anthropic2024mcp}. Systems that
combine models with conventional components are increasingly the norm
\cite{zaharia2024compound}. Cascades that route requests to cheaper models reduce cost
\cite{chen2024frugalgpt}; evaluations of agents increasingly report it alongside accuracy
\cite{kapoor2025agents}, and efficiency has long been argued to be a goal in its own right
\cite{schwartz2020green}; and a simple, non-agentic pipeline has outperformed open-source
software agents on real GitHub issues at a fraction of their cost \cite{xia2025agentless}. That
last result is closest in spirit to this paper. Where tool-making agents write a tool for their
own later use, \ferry{} is a tool written once, tested and shared, and the view it takes is that
a routine, rule-based task is better done by a small deterministic program, token-free, which
the agent calls when the task comes up.

\section{Limitations and future work}
\label{sec:limitations}

\begin{itemize}
  \item \textbf{Order dependence.} The case found in \cref{sec:eval-order} should be fixed, with
    a planning test that states the scenario, and the order-independence check kept as a
    regression test, ideally over random permutations rather than reversal alone.
  \item \textbf{Live measurements.} The agents' costs are estimated and their correctness is not
    measured; running real agents over the same histories would measure both. The Linear client
    is tested against Linear's published schema and against fakes, but not yet against a real
    workspace.
  \item \textbf{Polling and limits of GitHub's API.} Linear catches up only when \ferry{} runs; a
    template for running it on a schedule with GitHub Actions is planned. A search returns at
    most 1,000 results, the commit scan reads the first 100 commits of each pull request with up
    to 5 authors each, and \ferry{} reads the first 20 issues GitHub says a pull request will
    close (mentions in its text are not limited). Review requests to a team the user is on do
    not count as the user's own.
  \item \textbf{Scope and cleanup.} Commenting on an item or being mentioned in it does not bring
    it into scope; whether either should is an open question. When an item leaves the user's
    scope, its Linear issue stays as it is: nothing is ever deleted, but a Linear issue can
    outlive the user's involvement.
  \item \textbf{Retrying creates.} A comment whose creation failed in transit may be posted
    twice. Choosing the identifier of each new issue and comment on the client, which Linear's
    API allows \cite{linear2026schema}, would let \ferry{} retry creates without that risk.
  \item \textbf{Agent interfaces.} Agents use \ferry{} through its command line and read its
    text output. Machine-readable output, or a Model Context Protocol server
    \cite{anthropic2024mcp}, would let agents call it without a shell; neither exists yet.
\end{itemize}

\section{Conclusion}
\label{sec:conclusion}

\ferry{} brings a person's work in other organizations' GitHub repositories into their own
Linear workspace, with only their own credentials. It keeps its synchronization state in the
destination, in the metadata of the links between the two systems, and acts on edges in the
GitHub state rather than on its level, which gives idempotent reruns without a database and
leaves the user's edits alone. A pure planner, a client interface that cannot express the
forbidden writes, and eight explicit invariants make it safe to run in repositories that belong
to someone else; tens of thousands of simulated runs with failing writes found no violation of
them, and one ordering defect worth fixing. By this paper's estimate, an AI agent doing the same
job itself would process \TokLeanOpusHundred{} to \TokPlausibleOpusHundred{} tokens on a run of a
100-item route that finds a few changes, and cost nearly as much on a run that finds none; for a
team of 100, across \CmpModels{} models, that is \CmpItselfHundredMin{}--\CmpItselfHundredMax{} a year,
against \CmpDelegatingHundredMin{}--\CmpDelegatingHundredMax{} for agents that delegate to
\ferry{} and nothing on inference for \ferry{} alone. Both lessons generalize. A one-way copy into
a destination that has an owner of its own can keep its memory in the destination and act on
edges. And a routine, rule-based task that agents are asked to repeat is a candidate for
token-free automation: written once as a deterministic tool, it costs API requests instead of
inference, behaves the same on every run, and leaves the agent's tokens for the work that needs
them.
